# AskStatic onboarding and authoring plan

Date: 2026-10-10. Scope: how a new site owner gets good knowledge entries cheaply and learns what visitors ask that the chat cannot answer. No existing file was changed to write this.

## 0. What the code supports today (grounding)

| Fact | Where | Consequence for this plan |
|---|---|---|
| Entry = `id, language, title, questions[], keywords[], answer?, sources[{title,url}], clarification?, suggested, followUps[]` | `packages/astro/src/core/schema.ts` | Unknown YAML keys are silently stripped by zod. Any new metadata field (hash, origin, status) needs a schema change or must live outside the entry file. |
| Index fields boosted `questions 3, title 2.5, keywords 2, answer 0.5`; exact match on canonical title/question wins first | `engine.ts` (`BOOST`, `exactMap`) | Example questions are the highest-value authoring input. Keywords are the cheap place for synonyms. |
| Match gate: `minCoverage 0.6`, `minScore 2`, `gap 0.25`; negation and number mismatch force `disambiguate` | `engine.ts`, `converse.ts` `decide()` | Evaluation can reuse `respond()`; confident-wrong is already defined (see `eval/run.ts`). |
| Reply types `answer / clarify / disambiguate / fallback{no-match, low-confidence, clarification-failed}` | `converse.ts` | These are exactly the "unanswered" signals to capture. No new engine logic needed. |
| Validator: schema errors, duplicate id, missing follow-up/answer, cycles (errors); `no-questions`, `no-sources`, `duplicate-question` (warnings) | `validate.ts` | Ambiguity/duplicate checks exist for exact phrases only, not for overlapping vocabulary. |
| Source links checked against `dist/` | `astro/src/links.ts` | Reusable to resolve page URL -> built HTML file for hashing. |
| Loader reads every `.json/.yaml/.yml`, one entry or array per file, skips `_` and `.` prefixed names | `astro/src/knowledge.ts` | `_templates/`, `_generated/`, `_drafts/` folders are free: owners can keep unapproved material there and it never ships. |
| Options schema is `.strict()`: `knowledge, languages, defaultLanguage, pagefind, outputDir, thresholds, strict` | `astro/src/options.ts` | Every new option below must be added to `optionsSchema` or the build throws. |
| Hooks used: `config:setup`, `server:setup` (serves pack from memory in dev), `build:done` (validates, Pagefind, writes pack) | `astro/src/index.ts` | Build report and dev gap endpoint hang off these hooks; no new Astro hook needed. |
| Widget fetches `manifest.json` and one hashed language file; calls Pagefind on `fallback` for text input; no events, no telemetry | `astro/client/widget.ts` (~lines 291-370) | Feedback capture needs new widget code (the file already has uncommitted edits; coordinate). |
| Language pack: `stopwords, negations, stem, transliterate?` only. No synonyms. | `languages/types.ts` | A synonym layer is new (section 2). Must be applied at build time to keep the runtime small. |
| Real example: gkanev.com has ~75 entries; ~45 are generated by `scripts/askstatic-posts.mjs` (title, "What is X about?", tags unique to one post as "Have you written about X?"), the rest hand-written with 11-20 questions and 20-40 keywords (see `pricing.yaml`, `contact.yaml`) | `/Volumes/ROG/git/gkanev.com` | Generated entries are cheap but shallow; hand entries carry the intents (pricing, contact, hire, payment, NDA). The product should automate the generator and make the hand part guided. |

Observed gap in that real site: the hand-written intent entries (pricing, contact, hire, payment, nda, accessibility, privacy) are the ones visitors actually need, and each took 11-20 questions and 20-40 keywords written by hand. That is the cost to cut.

## 1. Install-time interview: `askstatic init`

### 1.1 Command surface

New package `packages/cli` (bin `askstatic`, depends on `astro-integration-askstatic`, `yaml`, `zod`; prompts via `@clack/prompts`). Same code can be called from `npx astro add astro-integration-askstatic` follow-up message ("run `npx askstatic init`").

```
npx astro add astro-integration-askstatic     # edits astro.config, installs
npx askstatic init                            # interview + scaffold
npx askstatic init --yes --type=saas          # non-interactive, templates only, CI friendly
npx askstatic init --scan-only                # skip interview, only run site scan
```

`init` is idempotent: it never overwrites a file that exists without `--force`, and re-running only adds missing intent files.

### 1.2 Flow (about 10 minutes, every step skippable)

1. Detect: Astro config, `base`, `i18n` locales, `src/content/*` collections, `public/llms.txt`, sitemap source, existing `src/askstatic/`. Pre-fill `languages` and `defaultLanguage`.
2. Site type (single choice, plus "other"): `saas, docs, portfolio/freelancer, agency, shop, blog, university/school, local business, nonprofit, community/open source`. Multi-select allowed (portfolio + blog is common).
3. Scan (section 1.4) and show what was found: "Found 38 pages, 12 blog posts, 1 FAQ page (9 Q/A), 3 FAQPage JSON-LD blocks".
4. Interview, adaptive: common block, then type block. Each question maps to one intent file (section 2.3). Owner picks "answer now", "use my page" (point to a URL, we extract), or "skip".
5. Write files, run `validateKnowledge`, print a coverage summary and the three next commands (`astro dev`, `askstatic gaps`, `askstatic eval`).

### 1.3 Question list

Answer formats: `text` (1-3 sentences, plain text, becomes `answer`), `url` (becomes `sources` and, if the page is in the build, the answer is drafted from the page's first paragraph with owner approval), `choice` (picks a template branch), `list` (comma separated, becomes bullets), `yesno+text` (yes/no selects wording, optional detail). `[skip]` = skippable with no file written; `[req]` = strongly recommended, init warns once if skipped.

**Common block (all site types)**

| # | Question | Format | Skip | Writes |
|---|---|---|---|---|
| C1 | What is this site / who is it for? (one sentence) | text | req | `about.yaml`, seeds `suggested` entry |
| C2 | Best way to contact you? (email, form URL, phone, chat, calendar link) | list + url | req | `contact.yaml` |
| C3 | Languages visitors write in? | list | skip | `languages:` option, pack selection |
| C4 | Opening hours / response time? | text | skip | `hours.yaml` |
| C5 | Physical location / service area? | text | skip | `location.yaml` |
| C6 | Pricing policy: public prices / "from X" / quote only / free | choice + text + url | req | `pricing.yaml` (wording chosen by branch) |
| C7 | Privacy: cookies, analytics, data collected, link to policy | yesno+text + url | skip | `privacy.yaml` |
| C8 | Accessibility statement URL, or "none yet" | url | skip | `accessibility.yaml` |
| C9 | Three questions visitors ask you most often (free text, one per line) | list | skip | seeds `questions:` of the nearest intent; unmatched ones become `_drafts/owner-questions.yaml` stubs with `answer` empty (not shipped) |
| C10 | Anything you never want the chat to answer? (topics) | list | skip | `_policy.yaml` (guard topics; see 1.6) |

**Type blocks (asked only for chosen types; max 6 questions each)**

SaaS: S1 plans and prices (list of `name: price`), S2 free trial / free tier (yesno+text), S3 refund / cancellation policy (text + url), S4 supported integrations or platforms (list), S5 login / sign-up URL and password-reset help (url), S6 status page, support SLA (url + text).

Docs / open-source: D1 install command(s) per platform (list; becomes a `clarification` with `field: platform`, see `demo/src/askstatic/en/installation.yaml` pattern), D2 supported versions and requirements (text), D3 licence (text), D4 where to report bugs / ask for help (url), D5 changelog / migration guide URL (url), D6 contribute / roadmap URL (url).

Portfolio / freelancer: P1 services offered (list; one entry per service), P2 availability for new work (choice: open / limited / closed + text), P3 rates and engagement types (hourly/project/retainer, from `engagement` branch of C6), P4 typical project size and timeline (text), P5 NDA / contract / invoicing terms (text), P6 remote / time zone (text), P7 speaking, press, CV URL (url).

Agency: A1 services (list), A2 industries served (list), A3 process in 3-5 steps (list), A4 minimum budget / typical timeline (text), A5 case study URLs (list of url, become sources), A6 team size and location (text), A7 how to request a proposal (url).

Shop: H1 shipping regions, costs, delivery times (text + url), H2 returns and refund policy (text + url), H3 payment methods (list), H4 order tracking / "where is my order" (url), H5 sizing or product help URL (url), H6 warranty (text), H7 wholesale / custom orders (yesno+text), H8 discount codes / newsletters (text).

Blog: B1 topics covered (list), B2 how to subscribe / RSS (url), B3 can people guest-post or sponsor (yesno+text), B4 reuse / licence of content (text). Posts themselves come from the scan, not the interview.

University / school: U1 programmes (list with URLs), U2 admissions: deadlines, requirements, how to apply (text + url), U3 tuition and scholarships (text + url), U4 campus location, visiting, open days (text), U5 student/staff directory and contacts (url), U6 careers and vacancies (url), U7 term dates (url), U8 accessibility and support services (url).

Local business / nonprofit / community: L1 services or programmes (list), L2 booking or donation / join flow (url), L3 prices or membership fees (text), L4 parking, access (text), L5 volunteer / careers (url).

Each answered question produces one entry with 8-15 seeded `questions` and 15-30 `keywords` from the intent template (section 2.3); the owner never types variants.

### 1.4 Auto-generation from existing content (no LLM)

New module `packages/cli/src/scan/` with pluggable extractors. Output is always `src/askstatic/_generated/<extractor>/*.yaml` plus a manifest `src/askstatic/_generated/.manifest.json`; nothing ships until promoted (1.5).

| Extractor | Input | Produces | Notes |
|---|---|---|---|
| `frontmatter` | `src/content/**` front matter | One entry per post/page: `title`, `description` as answer, `tags/categories` as keywords, URL as source | Productises `gkanev.com/scripts/askstatic-posts.mjs`. Keep its rule: only tags unique to one post become "Have you written about X?" questions; shared tags stay keywords. Skip `draft: true`. Real YAML parser instead of regex. |
| `html` | built `dist/**/*.html` (post-build) or `astro dev` crawl | Title from `<title>`/`h1`, answer from first paragraph under `h1`, headings as keywords, canonical URL as source | Reuses the URL-to-file mapping in `links.ts`. Respects `<meta name="robots" content="noindex">`. |
| `faq-page` | headings that end with `?` followed by paragraph(s); `<details><summary>`; `<dl>` on pages whose URL or title matches `faq|help|support` | Q/A pair -> entry; `questions[0]` = the heading text | Highest quality source: the owner already wrote the question and the answer. |
| `jsonld` | `application/ld+json` blocks: `FAQPage` (mainEntity Question/acceptedAnswer), `Service`, `Product`/`Offer` (price), `Organization`/`LocalBusiness` (contact, hours, address), `Event` | FAQ pairs -> entries; Organization/LocalBusiness -> contact/hours/location answers pre-filling C2/C4/C5; Offer -> price lines pre-filling C6/S1 | Structured data is trusted more than prose: marked `origin: jsonld` in the manifest. |
| `sitemap` | `sitemap-index.xml` or Astro `site` + routes | Section map (first URL segment) used for the coverage report (section 5.2) and to list pages with no entry | No entries are created from the sitemap alone. |
| `llms` | `public/llms.txt` / `llms-full.txt` | Link list with descriptions -> one entry per linked page (title, description, URL) | Treated like `frontmatter` for pages not otherwise found. |
| `headings` (fallback) | Any page with no better source | One entry per H2 section of long pages ("Pricing" section of a landing page) with `sources` anchored `#id` | Opt-in: noisy. |

Answer text is always extracted, never paraphrased: first paragraph, plain text, markdown links preserved, hard cap 400 characters, cut at sentence end, followed by the source link. Entries from extractors carry a short, conservative question set: the title, "What is <title>?" and, per extractor, headings turned into questions only for FAQ pairs.

### 1.5 How interview and auto-generation combine

Precedence per intent (highest wins, lower ones are shown as "also found"):

1. Owner answered in the interview (`origin: interview`).
2. Hand-edited entry already in `src/askstatic/*` (never touched by the tool).
3. JSON-LD / FAQ-page extracts (`origin: jsonld | faq`).
4. Front matter / html / llms extracts (`origin: page`).

Mechanics:

- Interview files live in `src/askstatic/<lang>/` (shipped). Generated files live in `src/askstatic/_generated/` (not shipped, because the loader skips `_` folders; this is deliberate).
- `askstatic scan` refreshes `_generated/` and prints a diff by page hash (section 5.3). `askstatic promote [ids|--section blog|--all-pages]` moves chosen generated entries into `src/askstatic/<lang>/` after a review screen (title, answer, sources, first 5 questions; accept / edit in `$EDITOR` / skip). Generated entries for content-heavy sites (blog posts) can be promoted in bulk, interview entries are reviewed one by one.
- Interview answers pre-fill from scan: if JSON-LD has an email, C2 shows it as the default. If an FAQ page exists, C9 is replaced by "we imported 9 FAQ entries; anything else?".
- Promoted entries get a sidecar record, not a YAML field (zod strips unknown keys): `src/askstatic/.askstatic-state.json` (committed) maps `id -> { origin, sourceUrl, sourceHash, promotedAt, lastReviewed }`. Phase 2 optionally adds these fields to `entrySchema` as `meta` (see roadmap).
- Collision rule: the tool derives ids as `post-<slug>` / `faq-<slug>` / `intent-<name>` and refuses to write an id that exists in `src/askstatic/`. The validator's `duplicate-id` already guards the build.

### 1.6 Files `init` writes

```
src/askstatic/
  en/                         # one folder per language chosen (loader walks recursively)
    about.yaml  contact.yaml  pricing.yaml  privacy.yaml  ...   # one file per answered intent
  _templates/                 # intent templates not yet filled in (skipped by loader)
    refunds.yaml  shipping.yaml  careers.yaml  ...               # answer: "" + TODO markers
  _generated/                 # scan output, not shipped
    .manifest.json
    frontmatter/*.yaml  faq/*.yaml  jsonld/*.yaml
  _drafts/
    owner-questions.yaml      # C9 questions without answers yet
  .askstatic-state.json       # hashes and origins (committed)
  _policy.yaml                # C10 guarded topics (see below)
astro.config.mjs              # only with consent: adds integration + knowledge path
src/components/               # nothing; user places <AskStatic /> (init prints the line, offers to insert in the main layout)
```

`_policy.yaml` is an idea that needs a code change: guarded topics become entries with `answer` set to a fixed deflection ("I can't help with that here, please use <contact>") and rich `keywords`; no engine change needed, they are ordinary entries tagged by id prefix `guard-`. This reuses the existing mechanism (negation/number guards) and keeps the engine untouched.

### 1.7 Optional LLM-assisted mode (separate opt-in layer)

Package `@askstatic/assist` (not a dependency of `core`, `astro` or `cli` by default). Enabled only by `askstatic assist ...` commands or `init --assist`. The deterministic path in 1.1-1.6 is complete without it.

- Provider: owner brings own key through env var (`ASKSTATIC_LLM_KEY`, `ASKSTATIC_LLM_PROVIDER`, optional base URL for local models). No key is stored in the repo; the CLI refuses to run if the key appears in a tracked file.
- Inputs sent: only the text of pages the owner selected, after the same extraction as 1.4; a dry-run `--show-prompt` prints exactly what would leave the machine, with token estimate and cost estimate, before any call.
- Outputs: only candidates in `_generated/llm/*.yaml`. Never writes to `src/askstatic/<lang>/`. Each candidate has: 8-15 questions, keywords, a short answer using only sentences present in the page (extractive instruction + a check that every answer sentence overlaps >= 80% of tokens with the source text, else rejected), and a confidence note.
- Human approval of every entry: `askstatic assist review` shows candidates one at a time with side-by-side source passage; `a` accept, `e` edit, `r` reject, `s` skip. Rejection is remembered (`.askstatic-state.json: rejected: [hash]`) so the same candidate is not offered again.
- Hash-based diffs: for each page, `sha256(normalized text)` stored as `sourceHash`. Rerun skips unchanged pages (zero tokens). Changed pages produce a "proposed update" against the existing entry (unified diff of answer and added questions); the owner approves or rejects. Deleted pages mark entries `stale` (section 5.3).
- Other assist tasks (each optional, each producing reviewed candidates): paraphrase generation for `questions` (section 2.4), eval-set growth (section 4.2), answering a gap from `askstatic gaps` using only site pages.
- Budget cap: `--max-usd` and `--max-pages`; abort and print partial results.
- Never runs in CI by default and never in `astro build`. The shipped pack contains no LLM-generated text that a human has not accepted.

## 2. Question and vocabulary expansion without an LLM

### 2.1 Where expansion goes

The engine tokenizes, stems (`en.ts` stem is conservative) and indexes `title, questions, keywords, answer`. Expansion must increase recall without lengthening the runtime or hiding negation/number guards. Approach: expand at build time into the existing fields, never at query time.

New build step `expandEntry()` in `packages/astro/src/core/expand.ts`, called from `buildPack()` (`packages/astro/src/pack.ts`) before `createEngine`. It returns a copy of each entry with extra terms appended to `keywords` only (keywords boost 2, answer 0.5, questions 3). It does not touch `questions`, so `exactMap` and the `duplicate-question` check stay precise, and expanded vocabulary is never shown to the visitor (they see `title`/`questions` only in suggestions).

### 2.2 Synonym and intent packs

New per-language data, in `packages/astro/src/core/languages/<code>.ts` next to `stopwords`: `synonyms: Record<string, string[]>` grouped by concept, e.g. `price: [cost, costs, fee, fees, rate, rates, charge, pricing, quote, estimate, budget, expensive, cheap, afford, "how much", money, pay, payment]`. `LanguagePack` gets an optional `synonyms?: readonly (readonly string[])[]` (array of equivalence groups).

Rules to avoid wrong answers:

1. A group is applied to an entry only if one of the group's words already appears in the entry's `title`, `questions` or `keywords` (the owner's own words trigger expansion; groups never inject new topics).
2. Added terms are stemmed through `lang.stem` like everything else and deduplicated.
3. Negations and numbers are never in groups (they are `lang.negations` / `isNumeric`, already special in `engine.ts`).
4. Cap: at most 25 added terms per entry.
5. Ambiguous words (`rate`, `charge`, `plan`, `book`, `post`) are in groups only together with a second word from the same intent ("hourly rate", "day rate") via phrase entries; single-word tokens that collide across intents are listed in `ambiguous.ts` and never expanded.

Intent vocabulary shipped as data (all lower case, per language, EN first, BG second as the repo already has a BG pack):

- money: price, cost, fee, rate, charge, quote, estimate, budget, afford, expensive, cheap, discount, free, deposit, invoice, refund, payment, pay, VAT, tax, currency words (eur, usd, gbp, лв)
- contact: contact, email, mail, phone, call, reach, message, write, address, whatsapp, form, support, talk to human
- hiring: hire, available, availability, freelance, contract, engage, work with, book, consultant, project, proposal, commission
- careers: job, jobs, career, vacancy, position, apply, opening, recruit, internship, volunteer
- support: help, support, problem, issue, broken, bug, error, not working, fix, ticket
- location: where, address, map, directions, located, office, visit, city, country, remote
- hours: hours, open, opening, closed, time zone, weekend, holiday, response time, sla
- policies: refund, return, cancel, cancellation, warranty, shipping, delivery, track, privacy, cookies, gdpr, data, accessibility, a11y, wcag

### 2.3 Common intents starter library (opt-in templates)

Ship `packages/cli/templates/<lang>/*.yaml` (and expose `askstatic add intent <name>`). One file per intent, valid entry shape but with `answer` omitted would fail the schema, so templates use a marker the CLI recognises (`answer: "TODO: ..."`) and live in `_templates/` until filled; `askstatic add` moves them out. The validator gets a new warning `todo-answer` (answer starts with `TODO`) so a template never ships by accident; `strict: true` turns it into a build failure.

Intents (id -> typical `followUps`): `pricing`, `contact`, `hire` (-> pricing, contact), `refunds`, `shipping`, `privacy`, `accessibility`, `hours`, `location`, `careers`, `support`, `login` (sign in, password reset, account), `docs` (where is documentation, getting started), `payment` (methods, invoices), `nda-contracts`, `languages`, `about`, `team`, `security`. Each template carries 10-20 questions, 20-40 keywords (modelled on gkanev.com `pricing.yaml` and `contact.yaml`), `sources: []` with a TODO, and optional site-type variants (`pricing.saas.yaml`, `pricing.quote-only.yaml`, `pricing.shop.yaml`) selected by the interview choice C6/S1.

Templates contain only placeholders in angle brackets (`<email>`, `<price>`) that the CLI fills from interview answers. Questions never mention a business name.

### 2.4 Paraphrases, typos, per-language

Deterministic generators, all run at `scan`/`add` time and written into the YAML so the owner can see and edit them (no hidden runtime magic):

- Question forms: from a canonical question produce template variants per language ("What is X?" -> "tell me about X", "X?", "do you have X"); EN and BG pattern lists in `packages/astro/src/core/languages/<code>.ts` (`questionForms`). Only 3-5 added per entry, flagged by a trailing YAML comment `# auto` so `askstatic lint` can count them.
- Typos: the engine already allows fuzzy 0.2 for terms of length >= 5 and prefix for >= 4 (`engine.ts`). Do not add typo strings to entries. Instead `askstatic eval --typos` mutates eval questions (swap, drop, double letter, adjacent key) to measure robustness (section 4.2). Short words (<5) have no fuzzy: the lint warns when an intent keyword shorter than 5 characters has no variant in keywords (e.g. `fee`, `job`, `pay`).
- Per-language packs: `registerLanguage` already exists (`languages/index.ts`). Add pack fields `synonyms`, `questionForms`, `intentVocab` as optional so community packs can ship them. BG keeps its `transliterate` channel; the CLI `init` offers to add Latin-typed variants only through that channel (no duplicate entries).
- Cross-language: `languages: ['en','bg']` produces separate packs per language, and ids resolve per language (`validate.ts key()`), so `init` writes the same id in each language folder and `askstatic lint` warns when an id exists in one language only.

### 2.5 Gap detection (static, before any visitor)

`askstatic lint` (also run by `astro:build:done` as warnings), new checks, all computed with `Engine.retrieve()` or token sets:

- `thin-entry`: fewer than 5 questions or fewer than 8 keywords on a non-generated entry.
- `intent-missing`: a common intent has no entry and the scan found a related page (e.g. page URL contains `pricing` but no `pricing` entry).
- `keyword-collision`: top-3 keywords of two entries overlap > 60% (pre-empts runtime disambiguation).
- `unreachable-question`: entry's own example question does not retrieve that entry as top candidate (self-eval, section 4.1). This is the most useful single check.
- `uncovered-page`: sitemap URL with no entry `sources` pointing to it (section 5.2).
- `short-keyword`: see typos above.

## 3. Feedback loop

### 3.1 What is captured

Event record (no PII by construction):

```json
{ "t": "2026-10-10", "lang": "en", "q": "do you ship to norway", "kind": "fallback|disambiguate|answer|clarify",
  "reason": "no-match|low-confidence|clarification-failed|ambiguous|negation|number-mismatch",
  "entryId": "shipping", "score": 3.4, "coverage": 0.8, "vote": "up|down|null", "page": "/shop/" }
```

Sources of truth in code: `reply.type` and `reply.reason` already come from `respond()` in `converse.ts`; `score` and `coverage` need `Reply` to carry the top `Candidate` (small change to `decide()` so `fallback`/`disambiguate` replies include `top?: { id, score, coverage }`). Never captured: IP, user agent, cookies, full URL query, anything the visitor did not type. Query text is truncated to 120 characters and a client-side scrubber drops tokens matching email, phone, long digit runs, or URL patterns, replacing them with `[redacted]`; if scrubbing removes more than half the text the event is dropped.

Widget API (change in `packages/astro/client/widget.ts`): dispatches `askstatic:event` as a bubbling `CustomEvent` on the element for every reply. Visitors may also use thumbs up/down under each answer (new two buttons, `aria-label`ed, shown after answers and Pagefind fallback results). With no sink configured the events are dropped, so privacy is the default.

### 3.2 Three sinks (owner chooses, default is local only)

New option in `optionsSchema`:

```js
feedback: {
  mode: 'off' | 'dev' | 'webhook' | 'endpoint',   // default 'dev'
  webhookUrl?: string,       // owner-supplied; POST JSON batch
  sampleRate?: number,       // 0-1, default 1
  fallbackOnly?: boolean,    // default true: only fallback/disambiguate/down-votes leave the browser
}
```

1. `dev` (default, zero network risk): during `astro dev`, `astro:server:setup` adds a middleware `POST /_askstatic/_event` and appends to `.askstatic/events.jsonl` (gitignored). The widget sends only when `import.meta.env.DEV`. Team members testing locally and the owner's own preview traffic populate it. Limitation, stated plainly: this captures the owner's tests, not production visitors.
2. `webhook` (owner-supplied): the widget `navigator.sendBeacon`s batches of events (fallback-only by default) to a URL the owner controls (Cloudflare Worker, Netlify function, Zapier, n8n, Slack incoming webhook via their own proxy). The package ships a 30-line example Worker in `packages/astro/examples/worker-events.js` that appends to KV/D1. We store nothing. CORS and rate limiting are the owner's job; documented. No third party is contacted unless `webhookUrl` is set; the URL is validated as https at build in `options.ts`.
3. `endpoint` (opt-in anonymous community endpoint, later): a hosted collector run by the project. Disabled until the project has a privacy policy, retention (30 days), and delete-by-site-key. Open question Q4 below recommends not building it for v0.1/0.2.

Consent: events contain visitor-typed text, so for GDPR the owner is the controller. The README must say: `dev` needs nothing; `webhook` needs a privacy-policy line; the widget offers `feedback.consent: 'always' | 'none'` and, if the site exposes `window.askstaticConsent === false`, nothing is sent.

### 3.3 Owner review

`askstatic gaps [--since 30d] [--file .askstatic/events.jsonl|URL] [--min 2]`:

1. Reads events (file, or `--from-webhook-export` for a JSONL dump the owner downloads).
2. Normalises each query with `canonicalPhrase` (`astro-integration-askstatic`) and groups identical and near-identical ones (same stemmed token set, or Jaccard >= 0.7).
3. Prints ranked clusters: count, example phrasings, reason mix, nearest existing entry (re-run `Engine.retrieve`) and its score.

```
 #  count  reason        example                               nearest entry (score)
 1   14    no-match      do you ship to norway                 shipping (1.2)
 2    9    low-conf      can i pay by invoice                  payment (1.8)
 3    6    disambiguate  cancel                                refunds / subscriptions
```

4. Interactive keys per cluster: `e` add as example question to nearest entry, `n` new entry (opens template for the closest intent, or blank), `i` ignore (stored in `.askstatic/ignored.json`), `g` mark as guard (adds to a `guard-*` entry), `u` open the page where it was asked.
5. Dev report page: `astro:server:setup` also serves `/_askstatic/_gaps` (HTML, dev only, shows the same clusters and "Add to ..." buttons that POST to a local `/_askstatic/_apply` handler writing YAML). Refused when `mode: build` or not dev. Not part of the shipped bundle.

### 3.4 One command from a reviewed question to a knowledge change

```
askstatic learn "do you ship to norway" --to shipping          # appends to questions: of entry shipping
askstatic learn "do you ship to norway" --new shipping-norway  # creates entry from the nearest intent template
askstatic learn --from-gaps --accept 1,2                        # batch: accepts clusters 1 and 2 from the last gaps run
```

Implementation: `packages/cli/src/learn.ts` parses the YAML with `yaml`'s `parseDocument` to keep comments and formatting (a plain `parse`/`stringify` would reformat the owner's file, which they would reject), appends to `questions`, runs `validateKnowledge`, re-runs the eval check for that entry (section 4.1), and prints the resulting reply type for the query ("now answers: shipping"). If the added question collides with another entry (`duplicate-question`) it is refused with the existing validator message. Hand-edited files are changed minimally (one line); generated entries are changed in `_generated/` and flagged `needs-promote`.

### 3.5 Thumbs

A down-vote on an `answer` event is high signal ("confident-wrong" in the field). `gaps` shows these in a separate section "answered but disliked" with the entry id; the fix action is `askstatic learn --move "<query>" --from <id> --to <id>` (removes the question from the first if present, adds it to the second) or edit the answer. Up-votes feed eval (section 4.2) as `expect: answer, id`.

## 4. Evaluation

### 4.1 Eval sets, by cost

1. Self-eval (free, always available): every entry's own `title` and `questions` must retrieve that entry. Implemented by iterating `Engine.entries` and calling `respond(engine, initialState(), {type:'text', text})`. Entries in a `clarification` group (children reached through a parent) are expected to land on the parent or the child (use `engine.parentOf`). Exact-match shortcuts make this trivially pass for the question itself, so the real value is the leave-one-out variant: remove question *k* from the entry, build the engine, ask question *k*, expect the same entry. This simulates "a visitor phrases it differently than the owner" with zero extra authoring. Needs a helper `createEngine(entriesWithout)` per entry (cheap: 75 entries x ~12 questions is under a second).
2. Generated paraphrases (free, deterministic): `questionForms` (section 2.4) applied to each question, plus typo mutations (`--typos`), plus synonym substitution from the synonym groups. Expected id = source entry. Labelled `kind: synthetic`; reported separately because they are easier than real queries.
3. Real queries (best): clusters accepted in `askstatic learn` append `{ q, expect: "answer", id }` to the eval file; rejected ones with `i`/`guard` add `{ q, expect: "fallback" | "guarded" }`. Thumbs-up events add positive cases.
4. Owner-written negatives: `askstatic eval --init` creates `src/askstatic/_eval/negatives.json` with 20 generic out-of-scope questions per language ("what is the weather", "who won the match", "write me a poem"), expected `fallback`/`guarded`; the owner adds site-specific ones (e.g. a competitor's product).

File format (same shape as `packages/astro/eval/questions.en.json`: `{ q, expect: answer|clarify|fallback|guarded|any, id? }`), stored at `src/askstatic/_eval/<lang>.json`; `_` prefix keeps it out of the shipped pack.

### 4.2 `askstatic eval`

Generalises `packages/astro/eval/run.ts` (which today loads fixtures from `test/fixtures` and only handles one language) into a CLI command that loads the real knowledge via `loadKnowledge` + `validateKnowledge` and builds the engine with the configured `thresholds`.

```
askstatic eval [--lang en] [--set self|synthetic|real|all] [--typos] [--json out.json] [--ci]
```

Metrics (per language and per site section, using each entry's first `sources[0].url` segment as its section):

| Metric | Definition (from `run.ts` semantics) |
|---|---|
| `correct` | reply matches `expect` (+ `id`) |
| `precision` | of replies of type answer/clarify, the share that match expectation: answers correct / answers given |
| `confident-wrong` | reply is answer/clarify but not the expected one (`confidentWrong` in `run.ts`). The number that matters most |
| `unanswered` | reply is fallback for a question that expected an answer (recall loss) |
| `over-answer` | answer/clarify given for a `fallback`/`guarded` negative (also confident-wrong, listed separately) |
| `disambiguated` | disambiguate replies when an answer was expected (acceptable but costs a click) |

Output: table, then the failing questions with got/wanted (as `run.ts` prints today), then for each failure the actionable hint (nearest entry and "add as question to X", "keywords overlap with Y").

CI gating: thresholds file or `askstatic.config` section (new option `eval: { minCorrect: 0.85, maxConfidentWrong: 0, maxOverAnswer: 0, minSelf: 0.95 }`); `--ci` exits 1 if breached, mirrors the current `run.ts` rule (`correct < 0.85` or more than 1 confident-wrong). Recommended defaults for owners: self-eval leave-one-out >= 90%, confident-wrong = 0 on real and negative sets, correct >= 85% on real. A GitHub Action snippet in the docs runs `pnpm askstatic eval --ci` before `astro build`. Also threshold sweeping: `askstatic eval --sweep` tries `minCoverage` 0.5-0.8 and `minScore` 1-3 and prints the best trade-off, then the owner copies the values into `thresholds` (the option already exists).

Caveat to document: the current EN 49/56 and BG 36/39 numbers (ACTION-PLAN.md section 0) come from an author-written set; the first release of the CLI should report self-eval and label it "optimistic until real queries are added".

## 5. Quality guardrails

### 5.1 Already there and what to add

Exists: `duplicate-id`, `duplicate-question`, `no-questions`, `no-sources`, `bad-source-url`, `missing-follow-up`, `missing-answer`, `cycle`, broken internal source links against `dist/`, `strict`. Add to `validate.ts` (all warnings): `todo-answer`, `thin-entry`, `answer-too-long` (> 600 chars; the widget shows plain text), `keyword-collision` (section 2.5), `follow-up-self`, `orphan` (entry not reachable from any `suggested`, follow-up, or clarification, informational), `language-missing` (id present in one language only). Ambiguity beyond exact phrases: compute pairwise overlap of stemmed question term sets using `indexTerms` and warn at Jaccard >= 0.8 between different entries (these will be `disambiguate` at runtime because of `gap 0.25`).

### 5.2 Coverage report

`astro:build:done` (and `askstatic coverage`) writes `.askstatic/coverage.json` and prints a table; input is the sitemap/`dist/` page list from the `sitemap` extractor and every `sources[].url` in the pack.

```
section      pages  cited  coverage  entries  suggested
/blog/         12     12     100%      12       0
/services/      6      3      50%       5       2
/docs/         40      4      10%       6       0
/contact/       1      1     100%       1       1
```

Rules: a page is "cited" if any entry source URL matches it (path without hash/query/trailing slash). Pages excluded by Pagefind selectors or `noindex` are skipped. Intent coverage is a second table (which of the section 2.3 intents exist and are non-TODO). No percentage gate by default; `strict` plus `coverage.minSection` (new option) can fail the build for chosen sections.

### 5.3 Stale-answer detection

Per entry with an internal source: `sourceHash = sha256(normalizedText(mainContentOf(page)))` where `mainContentOf` honours the Pagefind `rootSelector` (already an option) or `main`, strips nav/footer/scripts, collapses whitespace. Stored in `.askstatic-state.json` at `scan`/`promote`/`learn`/`review` time (`lastReviewed`).

At `astro:build:done` (page text available in `dist/`), compare current hash with stored; for each mismatch warn: `[stale] pricing: /consulting/ changed since 2026-09-02 (entry last reviewed 2026-08-10)`. `askstatic stale` lists them with a unified diff of the page text, and offers `ok` (mark reviewed, updates hash), `edit`, or in assist mode "propose update" (1.7). Tuning to avoid noise: ignore changes under 3% of tokens unless a number (`isNumeric`) or a currency/date token differs; numbers in sources are the high-risk case (prices, dates). Missing page -> existing `findBrokenSources` error. Optional `staleAfterDays` option (default off) warns for entries not reviewed in N days.

Entries with only external sources or interview answers have no hash; for interview entries `init` records `sourceUrl` when the owner gave one in the question.
